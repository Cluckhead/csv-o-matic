Programme explainer

Speeding up a workstream only brings launch forward if launch is waiting for it

The team halved the documentation estimate and launch did not move a day. Nothing was wrong with the documentation. Launch waits for the slowest chain of work, and documentation was not on it. After this page you should be able to look at a plan and predict, before anyone changes an estimate, whether the change will move the date.

The plan on this page is invented to make the mechanism visible; its numbers are not estimates for any real project. The model and its assumptions are under Limits.

01What decides the launch date?

Launch happens when the last piece of required work finishes. Everything else finishes early and waits.

The plan has two branches that start together on day 0. The build branch is a chain: design, then build, then integration, then validation, each starting when the one before it finishes. Documentation runs on its own. Launch needs both.

In the figure, each bar is an activity and its length is its duration in working days. The diamond is launch. A hatched stretch is time an activity sits finished, waiting for something else. The branch with no hatching is the one launch is waiting for; it is drawn with a heavier outline. Step through the plan a day at a time and watch what is in progress.

On day 10 documentation is done, and for the next ten days it does nothing but wait. Those ten days are spare: documentation could have taken ten days longer without anyone noticing. Nothing on the build branch has any spare time at all, which is what makes it the branch that sets the date.

02Does finishing documentation sooner help?

No. Documentation already finishes ten days early; finishing it earlier just adds to the wait.

Predict firstSomeone finds a way to do the documentation in 5 days instead of 10. What happens to launch?

Launch stays on day 20. Documentation now finishes on day 5 and waits fifteen days instead of ten; the build branch still finishes on day 20.

Drag the end of the documentation bar, or use the slider. Anywhere from 1 day to 20, launch does not move: whenever documentation finishes before the build branch, its duration only changes how long it waits. The ten days of spare time absorb the change, in either direction.

03Does finishing build sooner help?

Yes, day for day. Build sits on the branch launch is waiting for, so every day saved there is a day saved at launch.

Same plan, same scale; now only build can change. It opens at 8 days. and watch the diamond.

Launch moves to day 16, and the hatching on documentation shrinks from ten days to six. The four days did not vanish; they came out of documentation's spare time. Which raises the obvious question about how far that can go.

04So is documentation simply unimportant?

Only while it has spare time. Push it past 20 days and it becomes the branch launch waits for.

The tempting rule from the last two figures is “documentation doesn't matter, build does.” It is wrong, and the way it is wrong is the point of this page. Below, the original plan stays fixed on top; the plan underneath has its documentation estimate changed. Both use the same scale. Try .

At 22 days the heavy outline jumps to documentation, launch slips to day 22, and the build branch is the one with spare time. Which work matters is not a property of the work. It is a property of the current plan, and it changes the moment one branch overtakes another.

05Will a given change move your date?

Find the branch with no spare time. Changes there move launch day for day; changes elsewhere move it only once they use up the spare time.

Every activity can change here, and the original plan stays drawn in dashed outline for comparison. Before you touch anything, try one case you have not seen.

Predict firstValidation slips from 4 days to 7. Does launch move?

Launch moves to day 23. Validation is on the build branch, which has no spare time, so every day it slips is a day at launch.

Two habits follow from the model. Before approving an effort to speed something up, ask which branch it is on and how much spare time that branch has. And when an estimate grows, ask the same question in reverse: costs nothing, while costs two days at launch.

06What does this model leave out?

People. It assumes nobody works on both branches, and that is exactly where real plans most often break the rule.

The model knows about durations and dependencies and nothing else. Durations are treated as known, the two branches share no people, and changing one estimate leaves the others alone. Real plans violate all three, and the third one most often: the writer who finishes the documentation early may be the same person who then helps with validation.

None of that breaks the mechanism; it changes the inputs. If shortening documentation frees someone who then shortens validation, launch moves, but because validation got shorter, not because documentation did. The question to ask stays the same: which branch has no spare time, and does this change shorten it?

What would change the conclusion If documentation and build share the same people, documentation stops being independent: its duration then affects build's, and shortening it can move launch. Check who is on both branches before relying on the spare time.
Model and assumptions

Launch day = max(design + build + integration + validation, documentation). Each activity on the build branch starts when the previous one finishes; documentation starts on day 0. Spare time on a branch = launch − that branch's finish.
