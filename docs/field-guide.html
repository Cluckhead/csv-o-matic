CSV-o-Matic tells a model what is in a file, what is not, and when it cannot yet say

A typical question

“Portfolio PF003 holds Halvorsen Aerospace, but it is missing from the 13 November client holdings file. Why?”

The custodian sent SEDOL 417382; the security master holds 0417382. The join dropped the position. Follow it step by step.

When a security goes missing between two ETL steps, the answer is in the files: the last one that has it, the first one that doesn't, and the rule in between. The files run to gigabytes, so a model cannot read them. CSV-o-Matic reads them for it, on demand, and reports back in a deliberately narrow vocabulary. The habit that matters most: never treat “not yet known” as “not there”.

01What problem does CSV-o-Matic solve?

It lets a model trace one security through files it could never read itself, while leaving every conclusion to the model.

An ETL process is a relay race run by folders. Each step reads CSV files from one folder and writes new ones to the next, and every run leaves its files behind with a date and a timestamp in the name. When a security vanishes from a client report, nobody has deleted it. Some step, following its rules exactly, decided not to pass it on, and the evidence sits in two adjacent folders.

The trouble is size. A single vendor file can be several gigabytes, which is far too much to hand to a model and far too much to copy anywhere. So CSV-o-Matic answers narrow questions instead: which folders exist, which files are in this one, what are its columns, which rows hold this exact value, how many. It reads the file you name, from disk, at that moment, and keeps nothing afterwards: no database, no index, no cache.

The division of labour is strict. The model chooses which process, folder and file to look at, follows the chain upstream, and explains what it found. The server reports what is in the file it was asked about, and never writes to anything. That split is what makes the evidence trustworthy: the server has no opinion about the investigation, so it has no reason to round a “probably” up to a “yes”.

Four layers

Process
A named ETL flow and its steps, described in a maintained process map.
Folder
Where one step leaves its output. Only folders named in a process map can be read.
File
One CSV per run. Its name carries a business date and a run timestamp.
Row
One record for a security, matched by exact text and returned with its column labels.

03What can a search actually tell you?

One of three things: found, confirmed absent, or not yet known. Everything else in the design exists to keep those three apart.

match_found

At least one row holds the value exactly.

A match does not mean you have every match. Check results_are_partial.

confirmed_absent

The whole file was read cleanly and no row holds the value.

The only answer you may state as “it isn't there”.

inconclusive

No match was seen, but absence is not proven.

The scan stopped early, or the file could not be trusted. Never report this as absent.

“Not found” is the dangerous phrase, because it means two different things. It can mean the server read every byte and the value is not there. Or it can mean the server ran out of time, hit a broken quote, or noticed the file changing under it, and simply has not seen the value yet. A model that confuses the two is wrong in the most expensive way available: confidently.

So every search result carries an outcome, a scan block saying how far it got and why it stopped, and an explanation in plain words. The panel combines them the way the server does. It opens on a .

Now let the same search before it finds anything. The outcome becomes inconclusive, a cursor appears so the scan can carry on, and a count would be withheld rather than guessed.

The subtle case is a scan that : one with an unclosed quote, a wrong delimiter, or that changed while it was read. It has read everything, and the answer is still inconclusive, because rows may be hiding where the parser could not see them.

The rule, which holds for every combination on the panel: only a complete scan of a clean file can say “absent”.

06How does a search decide what counts as a match?

Exact text, whole field, nothing converted. Strictness alone would be unhelpful, so the server also reports near misses: values that are not matches but explain why there was none.

A row matches when the field equals the search value character for character. So 0417382 and 417382 are different values, Halvorsen does not match Halvorsen Aerospace PLC, and a trailing space makes a different value. That sounds pedantic until you remember what the downstream join does: it is exactly this pedantic, and it is the reason the position went missing.

Pedantry with no hints would leave the model guessing, though. So whenever nothing matches, the server says what nearly did. Type into the bench to see the four kinds of near miss. Near misses are never counted or returned as matches; they are leads, and they cost nothing extra because only rows containing the search text are examined anyway.

    07What changes when the file is six gigabytes?

    Searches take seconds to minutes, and come back in several responses. The time limit does not make a search faster; it decides how often you get to see where it has got to.

    Every search reads the whole file, start to finish, because only a complete read can prove an absence. So the first question about a big file is simply how fast it reads. The model opens on a . At the measured 440 MB/s that is about 14 seconds and one response, well inside the default two-minute budget.

    Now give it . One response carries at most 25, so the server stops as soon as it has seen a 26th, returns the first 25 with more_matches: "yes", and hands back a cursor. Five calls in all, and the same 14 seconds of reading, split five ways.

    File format matters as much as size. A 20 GB export with reads at about 55 MB/s, because every chunk has to be parsed in full. That is four calls and about six minutes. The first three stop at the time limit, and until the fourth returns, any “not found” is only inconclusive.

    A caller can ask for a to get early sight of progress. The total reading time does not change; the work is cut into more, shorter calls, each continuing exactly where the last stopped. Shorter budgets buy visibility, not speed.

    The controls need JavaScript. The result of each preset is described in the text and below the figure.

    What a partial response looks like

    When a response stops early it says so three ways: results_are_partial is true, more_matches is "yes" or "unknown", and the explanation starts with “PARTIAL RESULTS”. The server only says "yes" when it has actually seen another match, which is why it reads on to the 26th before stopping.

    Continuing with a cursor

    Send the same call with next_cursor and the scan resumes at the exact byte where it stopped. The cursor belongs to one search on one file: a different value, column or tool is refused, and so is any cursor once the file changes.

    Running out of time

    Cancelled calls return nothing The MCP protocol delivers no response to a request the client cancels. The scan stops within milliseconds and frees its slot, but the partial results go with it. To get partial results back from a long scan, set max_scan_seconds instead.

    09What happens when the file itself is wrong?

    The server explains what is wrong and withholds a verdict. A tool that read a broken file as if it were fine would report securities as absent when they are there.

    Requests that cannot be carried out

    A mistake in the request comes back as a structured error with a suggestion and the request echoed. For a search, the outcome is inconclusive, because no search took place.

    Files that cannot be trusted

    For these, copies of the 13 November custodian file were damaged in the ways real exports go wrong.

    10How does an investigation actually run?

    Question, route, symptom, source, the step where it vanished, and the rule that explains it. Two worked cases, every response real.

    Why did PF003's Halvorsen position vanish from the client report?

    “Portfolio PF003 holds Halvorsen Aerospace according to the custodian on 13 November 2026, but it is missing from the client holdings file for that date. Why?”

    1. Learn the route

      Which steps sit between the custodian file and the client report, and what does each drop?

      Positions go through enrich, then branch to client_report. Enrich is an inner join on SEDOL and drops anything unmatched. The report only excludes portfolios starting with INT.

    2. Confirm the symptom

      Is PF003 really absent from the client file?

      Yes: a complete scan, no match in any column, no near miss.

    3. See what the custodian sent

      What does PF003's row look like at the start?

      900 units of SecurityId 417382. Not zero quantity, so that rule does not apply.

    4. Find where it dropped out

      Did the position survive the enrich step?

      No. Zero rows for PF003 after enrich, so the report step never saw it.

    5. Ask why the join failed

      Is 417382 in the golden master that the 20:00 enrich run read?

      Not as such, but 0417382 is, in the same column.

    6. Name the near miss

      Which security is 0417382?

      Halvorsen Aerospace PLC.

    Conclusion

    The custodian sent Halvorsen's SEDOL for PF003 without its leading zero. Enrich joined on SEDOL as text, found nothing, and dropped the position. The client report is correct for what it received. Nothing failed. A zero went missing upstream, and every step downstream did exactly what it was told.

    Inferred, not observed: no file records which golden master a run read. The 18:30 file is assumed, because the 21:15 one did not exist when enrich started at 20:00.

    Why are there two prices for Larkspur on 13 November?

    “People are quoting two different prices for Larkspur Holdings for 13 November 2026. Why, and which did the positions use?”

    1. Look for more than one run

      How many golden files exist for that date?

      Two: 18:30 and 21:15. The process map says the later run supersedes the earlier.

    2. Compare the runs

      What differs for Larkspur between them?

      Only close_price: 452.1100, then 455.0000.

    3. Trace the change upstream

      Did the build change the price, or did its input?

      The vendor delivered twice, at 18:02 and 20:47, with different prices. The change came from the vendor.

    4. Check what positions used

      Which price is in the enriched positions?

      452.1100: the only enriched file ran at 20:00, before the corrected master existed.

    Conclusion

    Both prices are real. The vendor corrected Larkspur from 452.11 to 455.00 at 20:47, and the master rebuilt at 21:15 shows 455.00. Positions ran at 20:00 against the earlier master and were not rerun, so they are valued at 452.11. One is current; the other is what the published positions used.

    • Start with get_process_map; the filter rules often name the cause before any file is opened.

    • Say what is inferred. No file records which upstream file a run read.

    12Where do the examples and figures come from?

    The responses are real server output from invented data. The speeds are measured on generated files. The scan model combines the two with stated assumptions.

    Method and assumptions

    Examples. scripts/make_sample_data.py builds the invented processes' files; scripts/build_guide.py runs each example call through the server and embeds the responses in this page. Re-run it after changing the server and the examples refresh. Three broken custodian files are derived from the real one for section 09.

    Speeds. Mixed quoting and fully quoted: the large-file acceptance check on generated 2 GB, 120-column files, four-core cloud machine, file already in memory. Bare carriage returns and plain unquoted: one test on a 300 MB file with the same data. Real storage, especially a network share, will usually be slower than these figures.

    Scan model. Matches are assumed evenly spread through the file, each call reads at the stated speed from where the last stopped, a call stops on the 26th match (with 25 rows per response), at its time budget, or at the end of the file. Opening, header reading and response time are ignored, which flatters very short budgets.
