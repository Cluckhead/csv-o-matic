Field guide · a read-only MCP server for ETL files

CSV-o-Matic answers one narrow question about one file, and says whether the answer is found, absent or not yet known

On 13 November, 900 units of Halvorsen Aerospace vanished from a client report. Nothing failed. The files that explain it are far too large for an AI model to read, so CSV-o-Matic lets the model ask instead: which files exist, what columns they have, which rows hold this exact value. Every answer about a security is one of three things, and the product is built so that the third is never mistaken for the second. After this page you should be able to read any CSV-o-Matic response and say which of the three it is, predict which one a given question will get, and name the call that should come next.

A typical question: PF003 holds 900 Halvorsen Aerospace. Why is it not in the client report? The answer takes five calls. It is worked through in section 11.

Everything below happens on one evening, 13 November 2026, in two invented processes. The Security Master Build turns a vendor's reference file into a golden list of securities. End-of-Day Positions takes a custodian's holdings, joins them to that golden list, and produces a client report and a risk feed. Each step writes a CSV file into its own folder, and the real versions of such files run to gigabytes.

Most of the figures use one small file from that evening, the custodian's holdings, because it is short enough to see whole: eight records of four columns, listed in full under The custodian file, whole. Treat it as a scale model. The rules that govern it are the rules that govern a 6 GB file; only the waiting is missing.

01Why can't the model just read the file?

Because the file is a hundred thousand times larger than anything the server will hand back. So the model asks a narrow question, the server does the reading, and only the matching rows return.

Start with the simplest thing that could work: give the model the file. A real custodian file might be 6 GB. The server never returns more than 60,000 bytes in one response, a ceiling set in its configuration, and 6 GB is a hundred thousand of those. Even if the bytes could be delivered, finding one security by reading every row is the job computers have always done better than readers.

So the work is split. The model, which understands the question, decides what to look for and where. The server, which reads hundreds of megabytes a second, does the looking and returns only what matched. The first tool to meet is find_security_in_file: name a folder, a file, a column and a value, and get back the rows where that column holds that value.

The figure shows one such call, asking the custodian file for rows whose SecurityId is 0417382. Its left half is the file on disk, one row per record. The model never sees this half. The server reads the file a piece at a time: each numbered bracket in the margin is one read, and rows not yet read are hatched. A cell filled in teal is an exact match. The right half is the response, which is all the model ever sees. Step through the four reads.

Two things are worth noticing. The server found both matching rows in the first read and still made the other three, because it was asked for the rows where SecurityId is 0417382 and cannot say it has returned all of them until it has seen every row. And the response carries more than rows: scan.complete: true and more_matches: none are the server stating that it read to the end and there is nothing else. A response is an answer plus a statement of how far the answer can be trusted. Most of this page is about the second part.

At real scale the brackets are 4 MiB each and a 6 GB file has about 1,431 of them. The server skips, without parsing, any line that cannot contain the search text, which is how the project's own test reached 380 to 495 MB a second on a 2 GB file while holding no more than 63 MB in memory. That test was not re-run for this page; the figures are the README's.

02What can the server say if it has not finished reading?

Only that it has not found the security yet. Absent is a claim about the whole file, so it takes the whole file to make it.

The first model assumed the scan always reaches the end. It does not have to. Every scan has a time budget, 120 seconds unless the server is configured or asked otherwise, and a scan of a very large file on slow storage can outlast it. When the clock stops a scan part-way, the server has two honest things it can say and one dishonest one.

If it has already seen a match, it can say so: match_found. If it has seen none, it cannot say confirmed_absent, because the row might be in the part it has not read. That leaves a third outcome, inconclusive: not found yet, which is a different fact from not there.

Predict firstThe server is looking for Corbel Mining, 0629157. It has read three quarters of the file, found nothing, and run out of time. What should the response say?

It says inconclusive. Three quarters of a file with no match is suggestive, and suggestive is not what an incident report needs. Records 8 and 9 are unread, and Corbel could be in either.

The figure runs one call and lets the clock stop it after a number of reads you choose. It opens on Pendle Robotics, whose only row is the last in the file, with the clock stopping after two reads. Drag the budget up to four reads and watch when the outcome changes. Then switch to Corbel Mining, which is not in the file at all, and do it again.

Pendle's outcome changes from inconclusive to match_found only when the read that contains record 9 happens. Corbel's stays inconclusive through one, two and three reads and becomes confirmed_absent only at four, when nothing is left unread. Now try . OutcomeWhat the server is claimingWhat it takes

The rule for anyone reading a response, human or model: inconclusive is never evidence of absence. It is an instruction to continue, which raises the question of how.

03If a scan stops early, how does it ever finish?

With a cursor: a token in the response that lets the next call start where this one stopped. Without it, a time budget produces the same unfinished answer for ever.

An inconclusive answer that means continue needs a way to continue. The obvious way, calling again, does not work. The second call has the same budget as the first, starts at the same first byte and stops in the same place. On a file that takes five minutes to read under a two-minute budget, the model would never see the last three minutes of it.

So an interrupted response carries next_cursor. Pass it back and the scan resumes at the byte where it stopped, remembering how many matches earlier calls returned. In the figure the budget is counted in reads, because a 234-byte file takes no time at all; the real budget is max_scan_seconds, and a caller may ask for less than the server's limit but not more. The figure opens with room for one read per call and the cursor passed every time. First and see what the model learns. Then put it back and .

Without the cursor every call re-reads records 2 and 3 and reports, truthfully and uselessly, that Pendle has not been found yet. With it, four calls cover the file, and the fourth returns match_found with a note that the chain as a whole has read everything. Take the time away and the chain still takes four calls, not infinitely many: each call's first read is exempt from the clock, so every call moves forward.

Three properties of a cursor matter in practice. It belongs to one search: the same tool, file, column and value, so it cannot be spent on a different question. It belongs to the file as it was: if the file's size or modification time changes, the cursor is refused with invalid_cursor and the search starts again, which is right, because byte 140 of a rewritten file is not the same place. And it dies with the server process, since nothing about a search is stored anywhere.

The guarantee has an edge, found while testing this page Every call makes one read free of the clock, so a chain always advances as long as a record fits inside a read. Give the server one record longer than a read, which in practice means an unclosed quote swallowing the rest of the file, and a budget too short for a second read, and each call returns the same stopped_at_byte: the chain stalls instead of failing. With a longer budget the same file ends properly, in a parse_error or an unterminated-quote warning. Reproduced on the real server at small scale; at the default sizes it needs a record over 4 MiB. If two consecutive responses stop at the same byte, raise max_scan_seconds before calling again.

While a long scan runs

A scan that takes minutes should not be silent. A client that supplies a progress token is sent a notification every two seconds: megabytes read out of the total, matches so far, seconds used out of the budget. At most two scans run at once; a third waits its turn, and waiting does not use up its budget.

Cancelling a request stops the scan within milliseconds, but the protocol delivers no response to a cancelled request, so whatever was found is lost. To get a partial result on purpose, do not cancel: pass a short max_scan_seconds and read the response that comes back marked incomplete.

Back at real scale, a 6 GB file read at the README's 380 to 495 MB a second takes 12 to 16 seconds, well inside one budget. Put the same file on a network share reading at 20 MB a second and it takes 300 seconds, which is three calls and two cursors.

04Does one match mean you have every match?

No. A response holds at most 25 rows and 60,000 bytes, so match_found only ever means at least one. One field says whether there are more, and the same cursor fetches them.

Time is one reason a scan stops early. Size is the other. Ask the vendor file for every row whose ExchangeCode is XLON and 2,007 rows match; no response has room for them. So the server stops when the response is full: at max_rows rows, which is 25 unless the caller asks for fewer, or at the byte ceiling, whichever comes first.

The figure searches PortfolioCode for PF001, which matches four rows, under a row limit you set. It opens at two. Look at where the first call stops.

The first call does not stop when it has two rows. It stops when it meets a third, at record 6, and that is why it can say more_matches: yes and not merely perhaps: it has seen the next one. A clock stop can only say unknown. Give it and the single call returns them, then reads on to the end of the file before it will say none. more_matches: none is the only value that means you have everything, and like confirmed_absent it costs a complete scan.

When the number is wanted and the rows are not, count_matching_rows reads the whole file and returns only a count. Under a time limit it refuses to estimate: count stays null, and matches_seen_before_interruption gives the lower bound so far. When rows are wide, name the columns you need in columns; fewer columns per row means more rows per response, and a row too wide to fit at all comes back with its trailing columns left out and a note saying so.

05What counts as a match?

The whole field, character for character, as text. 0417382 and 417382 are different identifiers, and a search for one does not return the other.

So far a match has been taken for granted. The server's rule is the strictest available: a row matches when the chosen field equals the search text exactly, compared as text, capitals and all. Nothing is trimmed, nothing is read as a number, nothing matches in part. That is deliberate. Identifiers such as SEDOLs can begin with zeros, and a tool that helpfully treats 0417382 and 417382 as the same number has just merged two values that an ETL join treats as different, which is the very fault under investigation.

Predict firstHalvorsen Aerospace is held by three portfolios in the custodian file: PF001, PF002 and PF003. You search SecurityId for its SEDOL, 0417382, and the scan completes. How many rows come back?

Two: records 2 and 3. PF003's row holds 417382, without the zero, which is a different value. The response says, correctly, that every match was returned.

The figure holds the column fixed at SecurityId and lets the search text change. A dotted outline, used only here, marks a cell that a person would call the same security and the response never mentions. It opens on the search from the question above. Now , without its zero.

With 0417382 the response is complete and silent about record 5. Nothing in it is wrong, and nothing in it mentions PF003. With 417382 the server returns record 5 and adds something: near_misses, a note that two other values contain the search text inside a longer value. Near misses are never counted or returned as matches. They are the server saying: this is not what you asked for, but you may want to look.

Near misses have a blind spot, and it runs in one direction. They report values that contain what you typed. Type the short form and the long form shows up; type the long form and the short one is invisible, because 417382 does not contain 0417382. Capitals behave the same way: and the answer is a clean confirmed_absent with No near misses were seen either, two rows away from B7K2MN4.

So confirmed_absent has a precise meaning: no row holds exactly this text in that column. It is a statement about text, and it is the reader who turns it into a statement about a security. Before reporting something missing, try the forms it may have taken: with and without leading zeros, in the other case, under its other identifier.

06What if you search the wrong column?

You get a true answer to a question nobody meant to ask. The server says the value is not in that column and, if it saw the value elsewhere in the row, where.

A match is a value in a column, so the same value can be present in the file and absent from the search. The figure looks for PF003, a portfolio code, and opens on the mistake: searching SecurityId, the column a model reaches for out of habit when it has been asked about securities all day. Change the column.

In SecurityId the answer is confirmed_absent, and it is true: no security has the identifier PF003. The near miss is what rescues the investigation: the exact value appears in other column(s): PortfolioCode. Any column is a different tool, search_across_columns, which tests every field of every row and names the columns that matched. It is the right first call when you hold a value and do not know where it lives, and its confirmed_absent is the stronger one: the value is in no column at all.

Which raises the question of how a model learns a file's columns without reading the file. Two tools read only the header row. inspect_csv_headers returns the column names in their original order, with a few sample rows if asked; the response itself labels them a layout sample, not evidence about any security. search_column_names finds columns by a fragment of their name, which matters when a file has hundreds.

Column names are matched as strictly as values. Ask the golden master for SEDOL when its column is called sedol and no search happens at all: the response is inconclusive, with a column_not_found error and the names that came close. When a header repeats a name, rows label the columns name [col N] and one is chosen by position, as #N.

07Which file should you be searching at all?

The one the process actually read. The process map says which that is, and a file's name carries the two dates that matter: its business date and its run timestamp. The date on disk is neither.

Everything so far assumed someone had already picked the file. In an ETL estate that is most of the difficulty: a folder for every step, a file for every day, and sometimes two files for the same day that disagree.

The server reads a hand-maintained description of each process, the process map, and three tools answer from it. get_process_map lists the processes, or returns one in full: its steps, the folders each step reads and writes, how file names are built, which columns hold identifiers, and the rules by which rows are renamed, transformed and dropped. list_folders gives the folder inventory. list_csv_files lists what is in a folder now, with each file's size and the dates parsed from its name.

On 13 November the golden folder holds two files for the same business date. The map explains what that means: a second vendor file for one business date is a redelivery, and a later run timestamp supersedes an earlier one. The files show what changed: the 20:47 redelivery corrected Larkspur's price and added a security, Pendle Robotics, that the first delivery lacked, and the security master was rerun at 21:15. The map also says which file a downstream step uses: the golden master with the same business date and the latest run timestamp that existed when the step started. The positions step started at 20:00.

The figure draws that evening. The blue dot is when positions really started. Move the start time to ask what the same step would have written had it started later, for example .

At 20:00 only the 18:30 golden file existed, so positions read it: Larkspur is valued at 452.1100, and Pendle's 75 units find nothing to join to and are dropped. Start after 21:15 and both change. Neither positions file would be wrong. They are right about different inputs: the second delivery corrected the security master and never reached positions, because positions had already run. The 20:00 state is what the sample files hold; the other start times apply the map's rule and were checked against the script that generates the sample data.

Two cautions. The run timestamp is in the file name, and the server parses it for you as filename_tokens. filesystem_modified_time is only when the file was last written on disk, and in this sample every file carries the same one, 02:10 on 14 November, because they were all copied then. And the map is maintained by hand: the server reports what it says and does not check that the ETL obeys it.

08How do you compare one security across two files?

With one call, provided the server can tell which record in one file corresponds to which in the other. When it cannot, it says so and compares nothing.

Finding a security in two files and reading the rows side by side takes two calls and some squinting. compare_security_records does it in one: it finds the security in each file, pairs the columns by identical name, or by a column_mapping you supply when a step renamed them, and lists which values changed and which did not. Run on the two golden files for Larkspur it reports six values unchanged and one changed, close_price, 452.1100 against 455.0000.

That works because each golden file has one row per security. The custodian file has one row per portfolio and security, so Halvorsen appears twice in it and twice in the enriched positions. Which row should be compared with which? The figure opens on that question with no answer given. Give it one: .

Without a key the status is ambiguous_alignment and no lines are drawn: the server lists the records and the columns that tell them apart, and stops. It could have paired them in file order, and today it would have been right. Nothing about a CSV file promises order, and a comparison that is right by luck reports a 1,250-unit difference on the day the order changes. With PortfolioCode as the key each record has exactly one partner and the status is compared. Choose and it is ambiguous again for a different reason: both records on each side share that value, so the key picks out nothing.

The other securities show the remaining statuses. Larkspur has one record on each side and needs no key. is partially_compared: INT01 pairs up, and PF001's row exists only in the custodian file, which is the process map's rule that positions with a quantity of zero are dropped, made visible. is present_in_one_file_only.

Values are compared as exact text here too. Two values that differ only in spacing, capitals or number format, such as 1312.5 and 1312.5000, are still listed as changed, each with a note saying what kind of difference it is. 09What if the file itself is broken?

Then a complete scan that finds nothing proves nothing, and the server says inconclusive. It will not turn its own inability to read a file into a statement about a security.

confirmed_absent was defined as a complete scan with no match. There is an assumption hiding in that: the scan read the file the way the file was meant to be read. Exports go wrong in a small number of well-worn ways, and in each of them a search that simply looked for a matching row would find none and report the security missing.

The figure searches every column for Pendle Robotics, 0058213, and shows the file as the parser sees it. As delivered, Pendle is the last row. Now break the file: save it , leave , or export it .

With semicolons the file has one column, whose name is the entire header line; 0058213 is in there, inside PF001;0058213;75;GBP, and equal to nothing. With a quote opened in record 4 and never closed, everything after it, Pendle's row included, is the inside of one enormous field. As UTF-16, which is what a spreadsheet's Unicode text export produces, every second byte is zero and no text matches anything. Three different faults and one symptom: no row in which a column equals 0058213.

The server's answer in all three is inconclusive, each with its reason, and in the first two it also reports the near miss. A file the server cannot read reliably can produce match_found or inconclusive, never confirmed_absent. Even its matches are flagged: search the unclosed-quote file for 0417382 and the two rows it could read come back marked partial, with there may be more.

The server does not repair anything. It will not guess a delimiter or drop a stray quote; it reports what it saw and what has to change, which for the semicolons is the folder's csv_format in the process map. The same refusal covers requests it cannot carry out at all: a folder no process map describes, a file that does not exist, a name that is not .csv, compressed data under a .csv name. Each returns an error that names the problem and, where it can, the nearest thing that does exist. The full list is in the reference.

10Can you predict the answer before you ask?

You should be able to. Decide what text is being matched, in which column, and whether the scan will reach the end of the file, and the outcome follows.

Here the four things you have changed one at a time can change together: the text, the column, the row limit and the time budget, all on the clean custodian file. Before you touch anything, try a case this page has not shown.

Predict firstYou search any column for PF003, one row per response, with time for one read per call. The row turns up on the second call. After which call can the model say it has every match?

The fourth. Call 2 returns record 5 and runs out of time with more_matches: unknown. Calls 3 and 4 return no rows, yet their outcome is still match_found, because the outcome counts matches from earlier in the chain. Only call 4, which reaches the end, says none.

The controls need JavaScript.

Three more cases worth a moment each. stops on size, not time: two calls, the first saying yes. is the patient route to confirmed_absent: three inconclusive answers, then the one that counts. And is a clean, complete, misleading confirmed_absent that its own near miss corrects.

The habit to take away is a short checklist, in this order. Did the scan complete? If not, continue it. If it found nothing, was it the right text, the right column and the right file? Only after those is absent a finding.

11How does a real investigation run?

Map first, then files, then narrow questions, reading each answer for what it does not say. Three cases from the evening of 13 November; every response in them is real.

PF003 holds 900 Halvorsen Aerospace. Why is it not in the client report?

  1. How does a position reach the client report, and where can one be dropped?

    Positions are joined to the golden security master on SEDOL. A position whose SecurityId has no match there is dropped, silently and by design.

  2. Is PF003 in the client report at all?

    confirmed_absent from a complete scan of any column, with no near misses. The portfolio is not there in any form.

  3. Did the custodian send it?

    Yes: record 5, 900 units. But its SecurityId reads 417382, six characters where a SEDOL has seven.

  4. Does the golden security master know 417382?

    confirmed_absent, with a near miss: one value contains it inside a longer value, 0417382.

  5. Is that longer value Halvorsen?

    It is: Halvorsen Aerospace PLC.

Verdict The custodian's row for PF003 carries Halvorsen's SEDOL without its leading zero. The golden master holds 0417382; the join found no 417382 and dropped the position, so it never reached the client report. Observed: the four search results. Taken from the process map, not observed: that the join drops unmatched rows. Not established by these files: where the zero was lost before the custodian file was written.

Why are there two prices for Larkspur on 13 November?

  1. What price did positions use?

    452.1100, giving a market value of 18084.40.

  2. What did the vendor send that day?

    Two files, received at 18:02 and 20:47. The process map calls a second file for the same business date a redelivery.

  3. Do the two deliveries disagree about Larkspur?

    They do: 452.11000, then 455.00000.

  4. Did the correction reach the golden master?

    Yes, in the 21:15 rerun: close_price changed, the other six values did not.

Verdict The vendor corrected Larkspur's price at 20:47 and the security master was rerun at 21:15. Positions carry run timestamp 20:00, before the rerun existed, so they hold the first price. Both numbers are faithful to their inputs. Observed: both vendor prices, both golden prices, the positions price and every run timestamp. Taken from the process map: that positions read the latest golden file that existed when they started. Whether positions should be rerun is a decision, not a finding.

Corbel Mining is in the vendor file. Why is it not in the security master?

  1. Where along the pipeline does it disappear?

    present_in_one_file_only: in the vendor file, absent from the very next folder. Both scans were complete.

  2. What is different about the vendor's row?

    Its Status is DELISTED.

  3. Is there a rule about that?

    Rows where Status is 'DELISTED' are dropped.

Verdict Nothing is missing. Corbel is delisted, and the normalise step drops delisted rows before the security master is built. Observed: presence, absence and the status value. Taken from the process map: the rule. The files are consistent with the rule; they do not prove it is the only reason.

Rules of thumb

Read explanation first, scan.complete second.
Everything else qualifies those two.
Never report inconclusive as missing.
Continue with the cursor, or fix what the error names.
Before reporting confirmed_absent as missing, vary the question.
Other forms of the identifier, other columns, the other run of the file.
Take dates from the file name.
The time on disk records a copy, not a run.
Say what was observed and what was read from the map.
The server shows what is in the files; the map says what should have happened to them.

13What is real on this page, and what is not?

The data is invented, the responses are real, and the figures are a miniature that agrees with the server on every case tried. Speed is the one thing this page takes on trust.

The sample data is generated by a script in the repository and exists to contain things worth finding: a lost zero, a redelivery, a rerun, rows dropped by rule. The 67 responses embedded in this page were captured by running each call through the real server against that data; running the script again refreshes them, so they cannot drift from the product without someone noticing.

The figures do not replay recordings. They run a re-implementation, in this page's JavaScript, of the rules that decide a response: how the file is read in pieces, how records are split, what counts as a match and a near miss, when a scan stops, and how each outcome is worded. That miniature and the real server were given the same 3,218 searches and comparisons of the custodian file, clean and broken, under every row limit and time budget the figures offer, and returned identical results in all 6,702 calls. The time budget in those runs was counted in reads on both sides, so that an interrupted scan stops in the same place every time.

The miniature leaves things out, and the figures should not be read as covering them: the 60,000-byte ceiling, which the tiny file never approaches; encodings other than plain ASCII; files that end lines with a bare carriage return; files that change while they are being read; and anything to do with real elapsed time, queues or cancellation. Those behaviours are described here from the server's code and README, and are not demonstrated.

Three statements on this page are reasoned, not observed. That the stalled chain in section 3 would need a record over 4 MiB at the default sizes follows from the code and from a small-scale run, not from a 4 MiB test. That positions started at another time would hold another price follows from the rule written in the example process map. And the speeds are the project's own.

What would change the conclusions The three outcomes are only as good as the question. The server answers for the file, column and text it is given; choosing them remains the model's job, and a wrong choice produces a correct and misleading confirmed_absent. The process map is written by people. If it is out of date, the server will faithfully report a rule the ETL no longer follows. On storage far slower than the project's test machine, expect long scans to arrive as chains of cursors, and treat two responses that stop at the same byte as a fault, not as progress.
